## Pi upstream and MCP/codemode

Pi 0.99 introduced built-in MCP and codemode. By 1.1.0, Pi reads global `~/.pi/agent/mcp.json` and trusted project `.pi/mcp.json`; supports stdio and streamable HTTP, OAuth, user/project CLI operations, extension registration (`pi.registerMcpServer`), `/mcp`, and `direct`, `codemode`, `deferred`, and `hidden` tool exposure. MCP calls pass through Pi's tool hooks and permission gates. Codemode is a JavaScript tool for composing/searching tools in a sandbox; it is not a delegate-agent lifecycle engine. Sources: [MCP docs](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/coding-agent/docs/mcp.md), [codemode docs](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/coding-agent/docs/codemode.md), [0.99 changelog](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/coding-agent/CHANGELOG.md#L263).

The 1.1 source makes one constraint particularly relevant to delegation: at session start the built-in MCP extension starts connections for every enabled server in the loaded config in the background. The first prompt waits only for enabled servers with direct-exposure tools, and only up to its configured startup wait. Codemode/deferred connections also start in the background; a script/search waits for the needed tools when it uses them. Therefore an immediate subagent launch that resolves selectors from the current parent's registered tools can race with startup when the selected server is codemode/deferred. Sources: [MCP startup and wait path](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/coding-agent/src/extensions/mcp/index.ts#L1111-L1170), [exposure behavior](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/coding-agent/CHANGELOG.md#L209-L230).

The SDK is not equivalent to a full Pi CLI session: SDK sessions do not load built-in extensions by default, so an owned SDK runner must explicitly load MCP and, as required, codemode/tool-search. Source: [MCP SDK docs](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/coding-agent/docs/mcp.md#L256-L272).

Verified migration items from 0.87.1 to the 1.x line include the 1.0 change to fullscreen TUI by default (`tuiMode: "regular"` restores normal scrollback), and 1.0.3's breaking Azure provider key rename from `azure-openai-responses` to `azure` across auth/models/settings. Pi 1.0.0 also changed built-in extension source identifiers to `builtin:<name>`. The npm artifact no longer includes `npm-shrinkwrap.json`, so npm consumers do not get transitive dependency pinning from that file; use the Pi installer/runtime's pinned installation path if dependency pinning is required. These are verified examples, not an exhaustive breaking-change audit. Sources: [1.0/1.0.3 changelog](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/coding-agent/CHANGELOG.md#L78-L180), [built-in identifiers and npm packaging](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/coding-agent/CHANGELOG.md#L150-L165).

`pi-mcp-adapter` is not automatically obsolete just because core gained MCP. Pi documents that a loaded extension registering `/mcp` (including the adapter) replaces built-in MCP for that session, so Pi will not read `mcp.json` or connect its servers in that session. The adapter's 5.2.0 docs/changelog say an installed adapter without a custom config path writes `"-builtin:mcp"` into user settings once; if removing it to return to built-in MCP, re-enable the builtin (or remove the exclusion). Keep the adapter only if its extra import/config/search/scripting behavior is actually needed; that feature inventory and local use need a separate compatibility check. Sources: [Pi replacement rules](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/coding-agent/docs/mcp.md#L256-L272), [adapter config behavior](https://github.com/nicobailon/pi-mcp-adapter/blob/80fcdef8d9f6958751f1e225f88b272440caa542/docs/configuration.md#L55-L70), [adapter changelog](https://github.com/nicobailon/pi-mcp-adapter/blob/80fcdef8d9f6958751f1e225f88b272440caa542/CHANGELOG.md#L20-L30).

## pi-subagents 0.77.0 versus 0.73.1

The new release contains concrete improvements, not just version churn. Its changelog describes a smaller subagent tool schema/description, a built-in data-driven `parallel` workflow, more useful role/model typo suggestions, better async workflow result ordering/recovery and clearer completion metadata. The size reductions are release-author reported; this investigation did not independently measure token cost or latency. Sources: [0.77.0 changelog](https://github.com/nicobailon/pi-subagents/blob/1ac9b964eb9cda1662507c52f5277764637daccc/CHANGELOG.md#L1-L65).

It does **not** resolve all known issues relevant here:

- Built-in override precedence remains different from custom-agent merging. In `applyBuiltinOverrides`, a project override is returned immediately before the user override is read. A project `tools`-only override can therefore replace a global built-in model/thinking override. The adjacent custom-agent function explicitly merges user then project, retaining user-only fields. This is direct tagged-source evidence, not a runtime reproduction: [source](https://github.com/nicobailon/pi-subagents/blob/1ac9b964eb9cda1662507c52f5277764637daccc/src/agents/agents.ts#L1570-L1657).
- Built-in MCP selectors resolve synchronously from `runtimeSnapshotHost.getAllTools()`; the alternative metadata-cache path rejects entries older than seven days. There is no wait/retry in this selector resolver. Thus 0.77 bypasses the adapter metadata-cache requirement when native MCP is detected, but native MCP can still have a readiness race if a selector is resolved before the selected server connects. [Source](https://github.com/nicobailon/pi-subagents/blob/1ac9b964eb9cda1662507c52f5277764637daccc/src/runs/shared/mcp-direct-tool-allowlist.ts#L114-L155).
- After a selected builtin MCP tool has been resolved, child startup waits up to the configured MCP wait for that tool to become registered. The child wraps `createMcpExtension()` to narrow registered tool exposure but does not pass a server-subset config to that factory. Since core starts connections for all enabled configured servers, duplicate connections/process launches under fan-out are possible by source inspection; their number, cost, and actual impact were not measured. [Child MCP extension/allowlist](https://github.com/nicobailon/pi-subagents/blob/1ac9b964eb9cda1662507c52f5277764637daccc/src/runs/shared/child-session.ts#L267-L307), [child wait](https://github.com/nicobailon/pi-subagents/blob/1ac9b964eb9cda1662507c52f5277764637daccc/src/runs/shared/child-session.ts#L565-L581), [core connect-all behavior](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/coding-agent/src/extensions/mcp/index.ts#L1123-L1140).
- 0.74.0 removed `workflowScript` and `workflowScriptPath` in favor of one `workflow` input (inline block, script path, or named workflow). The changelog marks this as breaking; local definitions/callers using the old fields need migration before upgrading. Saved schedules/run records are said to remain compatible. [Migration note](https://github.com/nicobailon/pi-subagents/blob/1ac9b964eb9cda1662507c52f5277764637daccc/CHANGELOG.md#L180-L205).

**Assessment:** Updating from 0.73.1 is worth testing because the release has relevant fixes and usability improvements, but it is not yet a sufficient basis to promise deterministic role/model/tool selection. It still has the project-vs-global built-in override problem and an MCP selector readiness gap. The parent’s finalized session analysis counted 97 deduplicated launches from `.pi` sessions and 246 launches/709 calls across all projects. Observed needs for scripted workflows plus steering, interruption, stopping and resumption make this a runtime-qualification concern, not a reason to switch packages based on changelog claims.

## Concrete alternatives

These are real current packages, but none is a drop-in replacement across all observed workflow and lifecycle requirements.

| Candidate | What tagged sources show it does | Gaps against this workflow |
|---|---|---|
| **`@tintinweb/pi-subagents` 0.20.0** | Strongest alternative for controlled programmatic async delegation: event-bus cross-extension RPC for spawn/stop/consume, lifecycle events, parallel/scripted workflows, model/tools/thinking scope, structured output, per-agent persistence and workflow journal/replay. Model resolver supports exact/fuzzy lookup and same model across providers; this is provider resolution, not a configured fallback-model chain. The official Pi repository's subagent extension example is useful as SDK/CLI reference code, but it is not a maintained package with the persistent async management and recovery surface the workflow uses. It should not be treated as another drop-in candidate: [official example](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/coding-agent/examples/extensions/subagent/index.ts).

## Decision guidance

1. **Centralize the contract before changing engines.** Put role identity, exact model/provider policy, thinking, tool capability and output schema in one owned source. Expose one small typed programmatic facade for launch, status, steer/interrupt/stop, resume, and structured result. Bind it to the current subagent package first, then another engine only after its conformance gaps are explicit. This is the lowest-risk way to stop workflow scripts and direct delegation from drifting; it is an architecture recommendation, not a claim that any listed package already supplies the contract.
2. **Qualify 0.77 and Pi 1.1 before migration.** Fix or upstream the builtin agent override merge behavior, and test role resolution through both direct LLM tool calls and `workflow` launches with a project tools-only override. Test exact model/provider and thinking selection, unknown/unavailable model failure, fallback provenance, MCP selection immediately after startup for direct and codemode/deferred servers, and one parallel fan-out while counting actual MCP child processes/connections. Test stop/interrupt/resume and result schema through representative real scripts. Static source does not establish behavior under this user's config/runtime.
3. **Keep pi-mcp-adapter until a feature-by-feature audit demonstrates it is unnecessary.** Native MCP covers the standard server/config/OAuth/runtime path, but extension replacement semantics and adapter-only imports/search/scripts may matter. Before removing it, inspect current settings for `-builtin:mcp`; then restore built-in MCP and exercise the actual global/project server config in a disposable session. SDK runners must explicitly load native MCP/codemode resources.
4. **Do not switch to the alternatives as a cure by version number alone.** Tintin is the strongest alternative to prototype for programmatic delegation, but lacks lifecycle operations observed in the workflow and native MCP compatibility remains unverified. `pi-simple-agents` and `@mjakl/pi-subagent` are viable only if reducing requirements to simpler detached/fan-out or synchronous calls is acceptable.

**Limits:** This is registry and tagged-source research only. The release tarballs were statically inspected; no package was installed into Pi, no user configuration was edited, no historical sessions were independently reread by this research lane, and no live prompt, fallback selection, MCP connection count, token usage, latency or performance was measured. Treat the session counts and control requirements above as parent-provided session-analysis evidence.
