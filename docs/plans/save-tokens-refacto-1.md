Section 1 — Ownership and protocol save-tokens becomes a pure compression-and-telemetry extension. It stops calling pi.registerTool(...) entirely in local-tool-result-compressor.ts. Its only runtime hooks remain session_start, tool_result, the widget/status updates, and /compressor-stats. The compressor continues to inject details.compression into compressed tool results, but that metadata is treated as a data contract, not a rendering concern. We add a neutral shared protocol module outside save-tokens, following the same repo pattern used by protocol-style helpers like plan-auto-switch.ts. Proposed custom entry type: pi:compression:event. Proposed payload fields: toolCallId, toolName, timestamp, kind (compressed | skipped | failed), originalLength, compressedLength, savedBytes, savedPct, and reason for non-compressed outcomes. Only final outcomes are persisted; no partial tool updates. toolCallId is the stable dedupe key. The shared helper should expose small functions such as appendCompressionEvent(pi, payload), listCompressionEvents(entries), findCompressionEventByToolCallId(entries, id), and getLatestCompressionEvent(entries, toolName?). Other extensions consume that helper, not save-tokens internals. This keeps save-tokens replaceable, prevents dependency inversion in the wrong direction, and gives us one canonical place for event shape validation and replay semantics.

Section 2 — TUI behavior and consumer surfaces Immediate UI feedback stays in save-tokens, because that is part of telemetry, not tool ownership. On each final outcome, save-tokens should continue updating its footer widget and status line, and it should emit one concise per-tool ctx.ui.notify(...) message. Example messages: compressed bash: 1200 → 300 chars (-75%), compression skipped for read: no change, compression failed for grep. Since you asked for all three outcomes to be visible, the notification path should cover compressed, skipped, and failed, with a config switch to silence non-compressed outcomes later if the UI proves too noisy. Durable visibility comes from the shared pi:compression:event entries, not from transcript-rendered messages. For bash and safe_bash, owning extensions like sandbox/index.ts and safe-bash/index.ts can later choose to read result.details.compression and append inline footer text because they already own those tools. For read/grep/ls/find, the same rule applies: no inline footer from save-tokens; any inline rendering must be done by the owning tool definition or by a future pi core hook. In the extension-only path you chose, the supported UX for those tools is notification + widget + durable protocol entry, not footer decoration.

Section 4 — Error handling, rollout, and verification Error handling should stay conservative. If compression service calls fail, save-tokens must continue returning the original tool result unchanged, record a failed outcome with reason: service_error, and avoid repeated warning spam by keeping the existing one-time failure notification behavior. If result content is non-text, persist a skipped outcome with reason: non_text_content. If compression returns unchanged output, persist skipped with reason: no_change. That gives downstream consumers a full observability stream rather than only success cases. Verification should include: unit tests for createToolResultHandler(...) payloads, protocol helper tests for append/replay/dedupe, extension registration tests proving save-tokens no longer calls registerTool, and focused checks that sandbox / safe-bash continue to own bash / safe_bash without conflict. After tests, run bun test for extensions/save-tokens, extensions/safe-bash, and the new shared helper tests, plus bun run typecheck and bun run lint:check. Expected outcome: compression still works, all three outcomes surface in TUI and session entries, cross-extension consumers get a stable protocol, and ownership boundaries are restored.
